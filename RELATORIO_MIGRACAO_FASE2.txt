1. RESUMO DO QUE FOI ENTREGUE
--------------------------------------------------------------------------------
- Adapter de banco DUAL (server/src/database/adapter.js):
  · modo D1: env.DB via d1-binding.mjs (cloudflare:workers), prepare/get/all/
    run assíncronos, batch() atômico nativo, meta.changes/meta.last_row_id,
    undefined→null nos binds.
  · modo clássico: better-sqlite3 sync-exact (await sobre valor não-thenable
    é transparente — migrations, seed, scripts e testes com leitura direta
    funcionam inalterados).
- connection.js = shim que re-exporta o adapter → TODOS os módulos de
  negócio falam com o D1 sem nenhuma alteração de call site.
- db.js: better-sqlite3 carregado via eval('require') — invisível ao bundler
  do Wrangler (addon nativo não pode entrar no bundle; o Worker nunca
  executa esse caminho).
- worker.js (ES Module): Express oficial via cloudflare:node
  httpServerHandler (padrão oficial, compatibility_date >= 2025-08-15).
  app.js (CJS, inalterado da V3.5.0) integrado via interop de bundler.
- wrangler.toml: Static Assets servindo web/ (SPA fallback,
  run_worker_first=["/api/*"]), binding D1, vars de ambiente,
  nodejs_compat + nodejs_compat_populate_process_env.
- Guards de runtime Workers: config sem fs, rate limit sem setInterval
  (limpeza preguiçosa por request).
- d1/snapshot.sql: bootstrap completo (schema das 26 migrations + seed:
  módulos, empresas, usuários com hash scrypt, permissões, lojas).
- scripts/smoke-d1.sh: smoke de 3 passos para máquina real (health, login
  master = scrypt no workerd, /api/modules = adapter D1 ponta a ponta).
- pay/receive (payables/receivables): tx desnecessária removida — UPDATE
  condicional único (idempotência por changes===0 mantida).

3. DECISÕES REGISTRADAS
--------------------------------------------------------------------------------
- BLOBs (logo/comprovantes) permanecem como BLOB no D1 (limite 1 MB/row,
  coerente com os limites atuais de upload). R2 = upgrade path documentado
  se houver necessidade de arquivos maiores (metadados em D1 + bytes em R2).
- Migrations/seed são etapas de deploy (wrangler d1 migrations apply /
  wrangler d1 execute), NUNCA runtime do Worker (gate adapter.isD1()).
- database_id no wrangler.toml é placeholder local; produção exige
  `wrangler d1 create oficial-link-erp` e substituição do ID.

4. PENDÊNCIAS DA FASE 2 (fila objetiva, em ordem)
