1. OBJETIVO DA FASE 1
--------------------------------------------------------------------------------
Converter o ERP V3.5.0 (código 100% síncrono sobre better-sqlite3) para uma
API 100% assíncrona, estruturalmente pronta para o backend Cloudflare D1,
VALIDANDO a transformação pelos 258 testes originais ainda rodando sobre o
SQLite clássico. Princípio: await sobre valor síncrono é semanticamente
inócuo — logo a conversão mecânica é verificável pela suíte existente antes
de qualquer contato com o D1.

4. BUGS ENCONTRADOS E CORRIGIDOS (10 classes, todos evidenciados por falhas
   de teste ou por verificação programática)
--------------------------------------------------------------------------------
B1  Arrows anônimas em posição de argumento (router.get(..., (req,res)=>{}))
    nunca eram registradas como nós → async não inserido → await inválido.
B2  Callbacks de transição com arrow de EXPRESSÃO ÚNICA (sem chaves)
    escapavam do skip de corpos db.transaction.
B3  Arrow cujo corpo COMEÇA no await (body_start == pos do await) não era
    reconhecido como enclosing node (comparação estrita).
B4  Imports desestruturados const { f } = require(...) eram tratados como
    var.método → ~22 awaits de propagação perdidos (businessToday etc.).
B5  Template literals: código dentro de ${...} era marcado como string →
    awaits invisíveis (businessMonthStart escapou da propagação).
B6  Factory sync (manualRoute) virou async indevidamente → Route.post()
    recebeu Promise → crash em lote (28 arquivos em cascata, 1 causa).
B7  Arrows nomeadas const f = (...) => nunca recebiam nome no detector →
    callers de helpers locais (ex.: const one = async (sql,...p)=>...) sem
    await → payload de resposta virava {}.
B8  Inline-requires require('../x/service').fn(...) não rastreados pelo
    pipeline (só const = require era) → dashboard sem dados/gating.
B9  Precedência: await fn(...).prop = await(fn(...).prop) → .id/.c sobre
    Promise = undefined (role de usuário; 75 ocorrências de .get/.run/.all
    corrigidas com parênteses; varredura residual sem achados reais).
B10 async duplicado (async async function) em create/receive ao aplicar
    correções sobre funções já async.

Infra da sandbox (não do projeto): filesystem read-only intermitente
(vencido com gravação via tmp + os.replace) e limite de 120s por chamada
(vencido com suíte em background + polling do log).

Notas de integridade:
- SALE_REVERSAL é ENTRADA — cancelamento de venda não tem pré-cheque de
  saldo (mesma semântica da transação original).
- Cancelamento de COMPRA é SAÍDA — pré-cheque de saldo ANTES de qualquer
  escrita restaura o all-or-nothing (CANCEL-ROLLBACK).
- Janela de crash de processo entre escritas sequenciais: aceita na Fase 1,
  FECHADA pelo batch atômico do D1 na Fase 2 (adapter.batch já implementado
  e atômico no modo clássico via better-sqlite3 transaction).
